## 2. 必写文档(仅 3 份,均为开工文档)

### D1. 技术设计文档(TDD)— ✅ v1.2 已完成 → `docs/TDD.md`(261 行;v1.2 同步 M0 实现裁定:GLM 备用 LLM、超时组合、启动全量清扫、生命周期懒安装)
回答"怎么实现",PRD 回答"做什么"。篇幅控制在 300 行内,含:
- **编排器状态机**:`queued → planning → searching → fetching → synthesizing → completed / failed / scarce`,每态的持久化字段与超时策略
- **DB schema**(SQLite 起步):research_tasks、sources、research_cache(同地点 30 天回放,键 = 地名 + 坐标)三张表(anonymous_rate_limits 随 P1 限流功能再加)
- **API 契约**:POST /api/research(创建,SSE)、GET /api/research/:id/poll(短轮询)、GET /api/research/:id(刷新恢复)、GET /api/share/:token
- **SSE 事件协议**:`task_created / progress / search_hit / content / sources / done / error / continue_polling` 载荷结构
- **适配器接口**:`SearchProvider` / `LlmProvider` / `Fetcher` 的 TS 接口签名与降级链(博查→备选;DeepSeek→Qwen)
- 目录结构与模块划分(参考原项目 src 布局,去 Supabase/enterprise)

### D2. 研究 Prompt 规格(核心资产,闭源库)— M0 动工前写 v1,M0 期间迭代
这是产品灵魂,单独成文档单独版本管理:
- 规划 prompt:地名+坐标+方向预设 → 拆 5-8 个可搜索子问题(含行政区划层级信息注入,如"该点位于云南省大理州云龙县")
- 搜索词生成策略:子问题 → 博查 query(中英混合决策、时间限定词)
- 源筛选规则:去重(URL 归一化)、域名可信度权重、相关性打分
- 综合成文 prompt:章节结构、引用规则(只准用给定编号)、文风(通俗但严谨,拒绝导游腔)
- **资料稀缺降级策略**:源 < N 条时的降级模板(行政区划沿革 + 自然地理背景)
- **敏感规避策略**:近现代议题的处理边界(prompt 层规避 + 输出层过滤词表)
- 评估 rubric:好报告的 5 条可操作标准(溯源可查/结构完整/无编造/篇幅/可读性)

### D3. M0 验证方案 — M0 动工前,1 页纸
- 10 个测试地点梯度:知名(西安/敦煌)→ 中等(诺邓/碛口古镇)→ 冷门(某省保古桥)→ 极端无名(无名山沟,预期触发稀缺降级)
- 盲评表模板 + 评分人(≥3 人)+ 通过标准(≥7/10 "值得读完",成本 ≤¥0.25(与 PRD 统一口径,实际以实测确认),耗时 ≤3min)
- 失败时的迭代循环方式(prompt 改动 → 重跑 → 记录)
